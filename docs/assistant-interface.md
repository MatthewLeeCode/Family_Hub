# Assistant interface

Family Hub now has an **Assistant** destination. It uses the separate Rust assistant server through Family Hub's same-origin bridge. The web interface presents the account's state and submits commands; agent execution, scheduling, approval expiry, authorisation and workspace membership remain server responsibilities.

## Available now

- Enrolled local profiles sign in once through Family Hub, using their core account password. The assistant has no second credential form in this mode. Unconfigured installations retain the manual assistant connection. Guest and administrator-override sessions cannot use the assistant. Demo core accounts are `matt` / `demo-matt` and `nicky` / `demo-nicky`; see [enrollment and limits](assistant-authentication.md).
- Switch between the account's private workspace and its shared spaces. The selected workspace follows navigation within Assistant.
- Create conversations, send messages, retain unsent drafts while changing conversations or Assistant pages, and stop work. Enter sends; Shift + Enter inserts a line; IME composition does not accidentally submit. Drafts are kept in memory for the open page, not browser storage.
- Browse conversations in a panel shown only on Chat. It is on the right on larger screens and in a collapsed disclosure above the conversation on narrower screens.
- Open **Quick chat** at the bottom right from other destinations. It uses the same chat renderer, drafts, selected conversation, active job, stop action and permission status as the main view. Conversations are in a compact disclosure. **Expand** moves back to main Chat without submitting another request. Escape or Close collapses it and restores focus to the launcher.
- Open **Assistant controls** for Background, Memory and Activity. Background is its own destination; the section starts collapsed on Chat.
- Background displays required tools and separate availability/authority reasons. Bound follow-ups use an owner dependency review before Resume; older follow-ups retain direct Resume with an explicit **Dependencies not recorded** label. See [Background follow-ups](background-followups.md) for the contract and limits.
- Open **Permissions** under the same controls to edit your tool behavior, resource selections, connector access and expiry in the selected workspace. Saves use the current revision; a conflict retains your fields and asks you to reload. Changes apply to your grants, including in shared workspaces, and are checked by the core.
- Open **Connections** under Assistant controls for the account's current-workspace connector status: Ready, Offline, Review required, Disabled or Checking. It shows safe explanations, the configured tool count and the last health check. Quick chat remains available alongside it.
- See routine background updates as small inline text lines in main and quick chat. Cards are reserved for permission requests, questions and owner reviews. Requests from other conversations in the selected workspace are labelled so background work can be handled without leaving chat.
- Answer durable single-choice questions in main chat, quick chat or Background. No option is selected by default; Submit answer and Decline are explicit decisions. Questions belong to the current owner and workspace. Answering supplies task information and never grants permission for a later tool action. See [durable questions](user-questions.md) for response recovery and limits.
- Permission cards lead with a host-authored action summary, affected workspace/resource and a specific confirmation button. The one-action consequence and expiry stay visible; capability names, exact arguments and separately attributed connector descriptions sit under **Technical details**. Missing or unverifiable explanations hide confirmation and offer reload, while refusal retains its existing checks. See [clear permission requests](permission-requests.md).
- Inspect follow-up reasons, instructions, stop conditions, event triggers and remaining checks. Pause, resume or cancel a follow-up subject to the core's permission checks. Updates include the current revision so a stale screen cannot silently overwrite a newer decision.
- Read private remembered preferences and workspace activity. Shared spaces do not display the account's private memory.

The core's deterministic test agent can summarise sample inboxes, save important attachments, make local drafts, remember explicitly requested preferences and schedule inbox checks. Those actions exercise the same server contracts a different agent can use. Family Hub has not gained a live Gmail/Outlook integration or a language model through this view.

## Boundary and lifecycle

`static/assistant.js` owns the view. It uses the common `api()` helper and the explicit `/api/assistant/` endpoints. It makes no direct browser calls to the core address. Family Hub stores the core session server-side; this view never writes passwords or tokens into local storage or URLs. A password field is cleared as soon as a sign-in request starts. Account/profile changes discard local draft and conversation-selection caches.

Each view retains the public `assistant_context` returned by `/api/state` and sends it in `X-Assistant-Context`. The bridge rejects a stale context before reading or changing core state, even when another tab has already replaced the browser's shared cookie. Login/logout responses update only the initiating view's context. Other tabs receive a notification with no account data, clear private chat content and show **Reload Family Hub**. A rejected context or expired session also clears the view. This applies equally to main and quick chat; it prevents a draft composed for one account from being sent using a later account's cookie.

While an Assistant view or quick chat is active, updates are polled every 2.5 seconds, with one controller and one refresh running at a time. A quick chat beside Background shares its controller and snapshot with that page. Hidden documents skip polling. Quick chat stays mounted while navigating unrelated Family Hub pages; closing the last assistant surface cancels its timer. Mutations invalidate older snapshots; workspace changes disable the composer until the new conversation is loaded. Duplicate sends and conflicting answers to the same approval are suppressed locally. The server still performs the authoritative checks.

Opening or expanding a conversation does not submit a message. A send already in progress keeps its acknowledgement when its view is moved or closed, clears the accepted draft and retains the same conversation ID. A shared in-memory submission guard prevents a newly mounted surface from sending again while that request is pending. Profile/account changes discard this state; a stale quick chat displays a reload notice with no previous conversation content. The renderer checks view lifetime before touching the DOM; message submission checks account lifetime before updating shared state.

Messages and tool arguments are rendered as text, never HTML. Message updates preserve the composer and its draft. Background updates preserve expanded details and keyboard focus; if the acted-on control disappears, focus moves to the containing view. Expired approvals lose their Allow button even when the surrounding data has not changed.

Connections uses only `GET /api/assistant/connections?space_id=…` and `POST /api/assistant/connections/{id}/control`, through the same signed-in profile and captured view context. The bridge validates the exact workspace/action/revision fields, strips non-public response fields, rejects mismatched workspace or connection IDs, and maps unknown reason codes to a generic unavailable explanation. Executable paths, configuration, credentials and raw connector diagnostics are not exposed by these routes. Core authorization remains decisive.

**Retry** runs bounded discovery of the already reviewed connection; it does not call its tools or accept a review. **Disable connection** first presents an inline explanation and a separate **Disable and revoke access** button. It revokes that connection's standing permissions and pending approvals; already-dispatched work cannot be undone. **Enable connection** does not restore permissions or accept changed software or tools. Operator-disabled connections cannot be enabled here. Controls follow the server's `can_retry`, `can_enable` and `can_disable` flags, with an additional operator-disabled check.

Each connection action submits the displayed revision with its captured workspace and session context. Duplicate actions are suppressed while a request is pending, including across Assistant navigation. A conflict or uncertain response removes the controls and requires **Reload connection status** before another action; it never automatically repeats the mutation. Old workspace cards disappear immediately on a scope change, and late responses cannot replace the new workspace's list. Background health reads preserve focus and do not start probes. A validated session rejection in quick chat also clears an open Notes or Inbox view without waiting for its own next request.

All looks use this same view and command path. Colours, typography and spacing come from the current Family Hub look. The optional Quiet layout uses flat surfaces without gradients or the original grain overlay. Its chat bubbles and identity labels use the selected accent; question cards have a restrained accent tint and permission cards a muted amber tint. Text labels still distinguish their meaning. The original Family layout keeps its own styling.

## Remaining work

The current Family Hub slice includes main/quick chat, approvals, durable questions, follow-ups, constrained permission editing, connection controls and read-only memory/activity. [Inbox](inbox-interface.md) presents the core's sample mailboxes, local drafts and attachment filing status; attachment downloads, calendar and to-do still need corresponding destinations or commands.

Notes has a separate Rust-owned Family domain, a human editor and scoped read-only MCP tools. An optional, separately enrolled create-only writer can add notes through the core's permission gate, with Ask as its default. Existing reader connections remain read-only. The local synthetic demo was activated after the core's legacy Notes write path was retired and its existing note imported. See [Notes setup](notes-domain.md) and [Agent-created Notes](../domain/AGENT-NOTES.md) for schema-2 migration, enrollment and recovery limits.

Rich text rendering, attachment input, conversation search and memory deletion remain future work. Main and quick chat have identical current chat capabilities; neither accepts attachments or provides rich text rendering. Calendar and other agent-facing tools should be exposed through the core capability registry, with Family Hub supplying a scoped UI/domain adapter where appropriate.

Single sign-in is implemented for explicitly enrolled local profiles. Production identity isolation, transport security, passkeys and account recovery remain separate work. Do not treat the local demo passwords or Family Hub short passcodes as production credentials.

## Validation

`tests/test_personal_looks.py` covers authentication, role preservation, cross-profile isolation, field inheritance, malformed input, stale revisions, deletion and safe fallback. Run it with a writable local pytest directory on Windows:

```powershell
.venv/Scripts/python.exe -m pytest -q tests/test_personal_looks.py --basetemp .test-runs/personal-looks-check
.venv/Scripts/python.exe -m pytest -q tests/test_auth_bridge.py --basetemp .test-runs/auth-bridge-check
node --check app/bookhub/static/app.js
node --check app/bookhub/static/assistant.js
```

Browser checks use synthetic local data: sign-in, appearance save/preview reset, Quiet at 360 and 800 pixels, Compact desktop navigation, new chat and agent response, private/shared separation, exact-argument approval denial, shared follow-up creation/pause/cancellation, and keyboard focus after actions. Full → quick → full preserves an unsent draft. Sending immediately before expanding created exactly one user message and one server job, verified through the core API. Quick chat remains mounted through ordinary page navigation, shows waiting permissions, stops the pending job and updates Background from the same state. Its workspace selector stays in sync with Background. Closing restores launcher focus. Signing out removes quick chat, clears the previous shared-space draft and requires a new sign-in through the configured Family or legacy connection flow. The quick panel was also checked at 360 pixels. The permissions changed for the approval tests are restored after each check, and the synthetic watcher is cancelled.

For Connections, the auth/bridge suite passed **48 tests**, including fixed-route and input validation, response projection, wrong-workspace/item rejection, stale contexts, guest/admin-override denial and safe errors. JavaScript syntax and scoped whitespace checks passed. An isolated synthetic browser fixture verified Retry, Disable confirmation, Enable, operator-disabled controls, quick-chat draft/scope behavior, delayed and offline status loads, mixed-workspace responses, stale revisions, lost responses without duplicate actions, and a late probe response after switching workspaces. A context rotation without a broadcast caused quick chat's rejected request to clear both quick chat and the visible Notes view. Dark, Light, Paper and Blueprint were inspected; the main content had no horizontal overflow at 360 pixels. These fixture checks do not substitute for live core health integration checks.
